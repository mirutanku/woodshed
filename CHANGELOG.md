# Changelog

Dated log of completed work, decisions, and open issues. See CLAUDE.md for project context.

## 2026-08-17 — Independent playback volume (Web Audio migration)

**Problem:** iOS Safari pins `<audio>.volume` to 1 — the OS doesn't let a web page set it, only the hardware volume buttons can. Woodshed played recordings through a plain `<audio>` element, so turning up headphone volume to hear a quiet mic/instrument also turned up the backing track by the same amount, with no way to balance the two independently.

**Decision:** Rather than wrap the existing `<audio>` element with `createMediaElementSource()` (the smaller change), went with decoding recordings into an `AudioBuffer` and playing them through `AudioBufferSourceNode` + `GainNode`. Reasoning: Woodshed's tempo/auto-ramp feature depends heavily on `playbackRate`, and `createMediaElementSource` + `playbackRate` + gain has documented iOS reliability issues (WebKit bug #239696; mixed community reports of gain being silently ignored). The buffer approach avoids that combination entirely and gives sample-accurate seeking as a side effect. Trade-off: the whole file downloads and decodes before playback starts (no native range-request streaming), and sits fully decoded in memory while loaded — acceptable for practice-length recordings, worth revisiting if very long recordings become common.

**What changed:**
- New `frontend/src/useAudioEngine.ts` — shared Web Audio playback engine (play/pause/seek/restart/loop-a-segment/auto-ramp/volume), replacing the `<audio>`-element-based transport logic that was previously duplicated between the desktop and mobile players.
- `AudioPlayer.tsx` (desktop) and `MobileTuneDetail.tsx` (mobile) both rewritten to consume the shared hook instead of maintaining their own independent `<audio>` ref + rAF polling logic. This also fixes the pre-existing duplication between the two — previously mobile had a full second copy of the tempo/loop/ramp logic instead of reusing `AudioPlayer`.
- Volume slider added to both players, persisted to `localStorage` (`woodshed_playback_volume`), defaulting to 100% so existing behavior is unchanged until a user touches it.
- Loading state added (`isLoading`/`error` from the engine) since decoding takes a moment for longer files, unlike the old element's near-instant `preload="auto"` start.

**Bug found and fixed during verification:** `ensureContext()` only checked whether the cached `AudioContext` was null before reusing it, not whether it was `closed`. React 18 StrictMode double-invokes effects on mount (setup → cleanup → setup again, against the same refs) — the hook's unmount-teardown effect closed the one-and-only context during that dev-only cycle, and the guard handed back the dead context forever afterward: `ctx.currentTime` frozen at 0, nothing ever visibly played. Fixed by also recreating when `ctx.state === 'closed'`. Caught via a scripted Playwright run against the real dev servers (backend on Postgres, frontend on Vite) — not just `tsc`/`vite build`, which both passed the whole time and caught nothing here.

**Verified (desktop Chrome, scripted):** play/pause/resume-from-position, seek via timeline click, speed change while playing (presets + slider), segment looping with auto-ramp climbing speed across loop passes, volume slider updates gain, switching recordings resets cleanly. No console errors.

**Not yet verified — needs a real device:** the actual point of this change, independent volume on iOS Safari, plus the iOS-specific gesture/`AudioContext.resume()` timing and the previously-flagged `createMediaElementSource`-adjacent bugs this approach was chosen to sidestep. None of that is testable from a desktop browser. Next step is testing on an iPhone against a real audio interface.

**Also touched:** `AudioPlayer.css` / `ShedMode.css` — additive styles for the volume slider and loading/error states, no changes to existing rules.

## 2026-08-17 (follow-up) — Restore background playback

**Problem:** After the Web Audio migration above, playback stopped as soon as the user navigated away from Woodshed (e.g. switching to forScore to read sheet music) and only resumed on returning to the tab. The old `<audio>`-element player didn't have this problem. Root cause: a raw `AudioContext` connected straight to `ctx.destination` gets suspended/interrupted by iOS as soon as Safari is backgrounded, unlike an `<audio>` element, which iOS treats as a real background-eligible media session. The previous migration lost that for free by removing the element from the graph entirely.

**Fix:** `useAudioEngine.ts`'s `ensureContext()` now routes the graph's output through `createMediaStreamDestination()` into a hidden `<audio>` element instead of connecting directly to `ctx.destination`. Gain is still applied upstream in the Web Audio graph before the signal reaches that element, so the element's own (iOS-locked) `.volume` stays irrelevant and the volume fix is unaffected. `play()` now starts both the `AudioContext` and the bridge element synchronously, before awaiting either, to keep both inside the triggering user gesture. Added a `visibilitychange` handler that proactively retries `ctx.resume()` and the bridge element's `.play()` on returning to the foreground, so getting back to Woodshed shouldn't require the manual pause/play toggle that this exact class of bug tends to need elsewhere.

**Confidence level — lower than the volume fix.** This is the standard documented technique for this problem, but it doesn't have the same weight of community confirmation behind it. Checked a live GitHub issue (webamp #1279) where developers hit this exact problem in 2024 without landing a confirmed fix, and a production case (audiobookshelf #2655) showing that even native `<audio>`-element apps lose background playback specifically at points where JavaScript has to drive a state change — chapter boundaries there, our segment-loop restart here. That means: **plain single-track playthrough is the part this fix targets and might genuinely solve; a looped segment will very likely stop re-looping while backgrounded and just play through past the loop point**, since the loop restart depends on the rAF polling loop, which — like all JS — is throttled while the page is hidden. That's a known follow-on gap, not solved here; fixing it properly would mean moving to the AudioBufferSourceNode's native `loop`/`loopStart`/`loopEnd` so looping happens inside the audio graph instead of JS, which is a separate, deferred piece of work.

**Verified:** re-ran the full desktop Chrome scripted check from the entry above — no regressions in play/pause/seek/speed/loop/ramp/volume. Confirmed the bridge `<audio>` element is created, attached, playing, and receiving the `MediaStream`. Simulated Chrome's tab-freeze lifecycle state (`Page.setWebLifecycleState`) as a rough proxy for backgrounding — clock kept advancing and playback resumed cleanly across it — but this is explicitly not the same mechanism as iOS's app-switch `AudioContext` interruption, so it demonstrates the wiring doesn't crash, not that the fix works on iOS. **Still needs real iPhone testing**, specifically: does plain playback survive backgrounding now, and does a looped segment behave as predicted (stops re-looping) or worse than predicted (stops entirely)?

## 2026-08-17 (second follow-up) — Fix backgrounded looping and a pause/resume glitch

Real-device testing on the fix above came back: background playback itself now works. Two bugs on top of it:

1. **A looped segment blows through its markers while backgrounded** and only catches up on returning to the app — exactly the predicted gap from the previous entry.
2. **Pause stopped working reliably**, producing rapid stutter and slight distortion on resume.

**Fix for (1):** `startSourceAt()` now configures the source node's native `loop`/`loopStart`/`loopEnd` instead of driving the loop from the rAF polling loop (jump back to `loopStart` every time polled position crossed `loopEnd`). Wrapping now happens inside the audio graph itself, with no JS involved, so it keeps working while the page is backgrounded and rAF is throttled. `computeCurrentBufferTime()` now simulates that same wrap in its own bookkeeping (display position, detecting when a pass completes for auto-ramp), since the graph's real wrap is invisible to JS-side clock math otherwise.

**Fix for (2), root cause:** `pause()` was stopping the upstream `AudioBufferSourceNode` but never actually pausing the bridge `<audio>` element consuming its stream — it was left "live," rendering a `MediaStream` that had gone quiet, which is what produced the stutter/distortion. `pause()` now calls `.pause()` on the bridge element too.

**A second bug caught during re-verification, not yet shipped:** the native-loop rewrite for (1) introduced a new clock-desync bug of its own — `computeRawBufferTime()` deliberately never rebases during ordinary looping (by design, so the wrap math in `computeCurrentBufferTime()` has something to wrap), so turning a loop off mid-playback without rebasing left it reporting a huge unwrapped number as the "real" position. That falsely tripped the end-of-track check on the very next tick and silently killed playback — which would have looked like a second flavor of "pause doesn't work," this time triggered by clearing a loop rather than by pausing directly. `loopOff()` now rebases the clock using the still-wrapped position before clearing loop state. Caught by scripted verification before reaching a device, not from another user report.

**Verified:** re-ran the full existing scripted regression suite (play/pause/seek/speed/volume, no regressions) plus new targeted cases: pause while a loop is still active (position holds, resumes correctly), clearing a loop mid-playback (playback continues, doesn't silently reset to 0:00 — the exact new bug above), and pause after clearing a loop (now actually pauses, holds position). Auto-ramp's climb-per-pass behavior re-verified unchanged under the new native-loop-based pass detection. **Not verified:** actual audio quality (headless testing checks state/timing, not waveform — the "gapless" claim for native looping vs. the old hard-restart-per-pass approach is inferred from how the API is documented to behave, not heard). Needs another round of real iPhone testing, specifically: does a looped segment now survive backgrounding, and is pause/resume clean.
